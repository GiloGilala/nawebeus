## 5. Defect register (verified in the working tree, 2026-09-20)

Severity: **C**ritical (product unusable / data or security at risk) · **H**igh · **M**edium · **L**ow.
All are pre-existing; none are introduced by this roadmap.

| ID | Sev | Defect | Evidence | Impact |
|---|---|---|---|---|
| **F-01** | C | **Signup creates the owner membership without a role.** `src/services/auth/signup.ts:182` inserts `organization_members (organization_id, user_id, status, is_active)` with no `role_id`. `loadAbility` (`src/services/auth/ability.ts`) derives permissions via `om.role_id → role_permissions`; NULL role ⇒ zero permissions. A brand-new org owner can authenticate but **every `requireAbility`-guarded route returns 403** — they cannot invite members, cannot update the org, cannot manage anything. No test asserts the owner's role after signup (`src/tests/auth/signup.test.ts` has no role/permission assertion). | Onboarding dead-end; the product is unusable after signup |
| **F-02** | H | **Permission subject mismatch: `organization` vs `org`.** `src/app/orgs/org.route.ts:40` calls `requireAbility("update", "organization")`; the seed (`src/seed.ts:63-84` region, `org.read`/`org.update`/`org.delete`) parses in `loadAbility` to subject `"org"`. `ability.can("update","organization")` finds no rule ⇒ **`PATCH /api/orgs/:orgId` 403s for every user, every role.** (Verified against CASL v7 semantics, §5 note.) | Org settings unchangeable via API |
| **F-03** | H | **MFA 2-step login is a dead end.** `signIn` returns `{requiresMfa:true, sessionId:userId}` with no cookie (`auth.service.ts:158-166`; `signin.route.ts:46-54`), but **no route exists to submit the code**: `confirmMFAChallenge`/`checkMFAForLogin` in `src/services/auth/mfa.ts:175-202` are called from nowhere (grep-verified). Only the single-round-trip `mfaCode` in the signin body works. A client implementing the standard challenge flow can never log in as an MFA user. | MFA users locked out via the documented flow |
| **F-04** | H | **MFA backup codes: displayed ≠ stored.** `initiateMFASetup` generates and returns codes A (also written to DB, `mfa.ts:30`); `confirmMFASetup` **regenerates a fresh set B and stores B** (`mfa.ts:63`). The user keeps codes A; the DB has B ⇒ every displayed backup code fails. | Backup recovery broken — defeats MFA usability and recovery path |
| **F-04b** | M | **Backup codes stored in plaintext** (jsonb array of UUID slices) vs spec AC4 "stored as bcrypt hashes". | Credential-at-rest exposure |
| **F-05** | H | **User status never enforced at sign-in.** `signIn` selects `status` (`auth.service.ts:73`) but never checks it: `suspended` accounts (settable by admin at `PATCH /api/users/admin/:userId`) and `pending_verification` accounts can authenticate and act. PRD 8.1.1/8.1.2 and Module 1 spec require verified + active for access. | Suspended users retain full access |
| **F-06** | H | **The org-scoping CASL condition is inert.** `loadAbility` attaches `{organizationId: orgId}` to every rule, but `requireAbility` checks `ability.can(action, "string-subject")`. In CASL v7, `Rule.matchesConditions` returns `true` for subject-type (string) subjects whenever the rule is not inverted — the condition is only evaluated for object subjects (verified in `@casl/ability` v7 dist source, `matchesConditions`). Tenant isolation therefore rests **entirely** on JWT-derived `orgId` + `requireOrgMatch` + service-level org predicates (which are all present and correct today). Consequence: the documented 3-layer defense (Security Architecture §4.3) is 2 layers at the API tier; and any future developer who omits `requireOrgMatch` on a new `:orgId` route, believing the ability condition scopes it, will ship a cross-tenant hole. | Latent architectural security risk; misleading security docs |
| **F-07** | H | **Role self-protection guards reference role codes that don't exist.** `role-assignment.service.ts` enforces "cannot demote owner" (code `owner`), "owner can't remove own role" (code `owner`), "cannot remove last Admin" (code `admin`). The seeded roles are `super_admin / org_admin / member / viewer` (`src/seed.ts` roleDefs). No role with code `owner` or `admin` exists ⇒ none of the guards can ever fire. Related doc/code conflict: spec calls for a 6-tier hierarchy (Owner, Admin, Manager, Creator, Analyst, Viewer); PRD §8.2.2 for 5 (Owner, Admin, Manager, Analyst, Viewer); seed has 4 different ones. | Lockout protection absent; role model unaligned across all three sources |
| **F-08** | C | **Invitation flow is one-way: no accept endpoint.** `inviteMember`/`bulkInviteMembers` create `organization_members` rows with `status='invited'` + token and email a link to `${CORS_ORIGIN}/invite?token=…` (`invitation.service.ts`), but there is **no service function or route to accept an invitation** (grep-verified: no `accept*invitation` in `src/`). The invitee — whether brand-new or existing user — can never become an active member. Combined with F-01 (no role assignment at join) the whole team onboarding path is broken. | Team onboarding impossible |
| **F-09** | M | **Signup verification email link is broken.** Link base `${config.CORS_ORIGIN}/verify-email?token=…` (`signup.ts:211`); the actual route is `GET /api/auth/verify-email` (`verification.route.ts`). The resend path builds `${origin}/api/auth/verify-email` where `origin` is the **client-sent `Origin` header** (`verification.route.ts:34`) — arbitrary value embedded in a security email. | Verification emails from signup dead; origin spoofing into emails |
| **F-10** | M | **Inconsistent client-IP extraction.** `signin.route.ts:38` reads `CF-Connecting-IP ?? X-Forwarded-For`; `authMiddleware.clientIp` reads `x-forwarded-for ?? x-real-ip`; no trusted-proxy configuration exists. Behind the documented nginx (Infra §3.5) the rate-limit key and session `ip_address` can disagree per request, and both are spoofable without proxy hardening. | Rate-limit key instability; IP logs unreliable |
| **F-11** | L | **Route shadowing:** `adminRouter` mounted at `/users` defines `GET/PATCH/DELETE /:userId`; `meRouter` (registered first) owns `/me*`. Harmless today only because registration order shadows it; any reorder makes `GET /users/me` an admin call with `userId="me"`. | Latent |
| **F-12** | H | **Sliding-window rate limiter stops working permanently after the first window expires.** `checkRateLimit` upsert: `ON CONFLICT (key) DO UPDATE SET count=count+1 … WHERE rate_limits.window_start >= windowStart`. Once a bucket's `window_start` is older than the current window, the `DO UPDATE` is skipped **and the `window_start`/`count` are never reset**; the subsequent `SELECT … WHERE window_start >= windowStart` finds no row and returns `false` — forever. No job reclaims rows (`rate_limits_expires_at_idx` exists "to support reclaiming" but nothing reclaims). So the IP brute-force block (BR-AUTH-018) dies permanently per IP after ~30 minutes. (Table itself was only added 2026-09-13 — before that the limiter failed open on every call, per `db/core/rate-limits.ts` header comment.) | Brute-force protection expires permanently per bucket |
| **F-13** | M | **CORS is open to all origins.** `app.use("*", cors())` with no options in both app factories (`src/server/index.ts:13,41`); `CORS_ORIGIN` is loaded by `config.ts` but never used. With `SameSite=Strict` cookies the practical XSS-to-session risk is reduced, but the API accepts credentialed cross-origin preflights from any origin. | Over-permissive CORS |
| **F-14** | M | **No pagination on list endpoints** (`GET /api/users/admin`, `/orgs/:orgId/members`, sessions, api-keys return full sets). Fine at beta scale; will degrade. | Scale |
| **F-15** | L | **Session device metadata never populated** — `device_type/device_name/browser_*/location_*` columns exist and are returned by `listUserSessions` but always null (no UA parsing in `createSession`). PRD 8.1.2 device tracking partially unmet. | Feature gap |
| **F-16** | M | **`users.organization_id` one-org model vs agency persona.** PRD 2.4 (agency: "isolated workspaces for every client; one login") implies multi-org membership + org switching; schema supports memberships but JWT/session/abilities are single-org; no org-switch endpoint exists. | Blocks agency workflow; decide in D14 |
| **F-17** | L | **`createApp()` (no-DB factory) is production-dead code** — only `createAppWithDb` is used (`src/index.ts`); `createApp` exists solely for tests that never even use it (tests use `createTestApp` = `createAppWithDb` with no-op db). | Dead code |
| **F-18** | L | **`purgeExpiredAccounts` exists but is never scheduled** (no scheduler exists). Purge of deleted accounts will not happen until Phase 2 lands the scheduler — NDPR erasure clock runs. | Compliance clock |
| **F-19** | L | **Audit log has no read API** (only `writeAuditLog`); PRD Module 10 / admin requirements need query + retention. | Feature gap (planned in P1-002/P14.13) |
| **F-20** | H | **Invite-send path was schema-broken: every invite 500s.** `inviteMember`/`bulkInviteMembers` (`invitation.service.ts`) write columns that did not exist on `organization_members` — `invitation_token`, `invitation_token_hash`, `invitation_sent_at`, `expires_at` (PG 42703) — and insert `user_id = NULL` for invitees without an account, which the schema forbids with `user_id NOT NULL` (PG 23502). So even a user holding `members.create` (e.g. the seeded super_admin) could not send a single invitation. Discovered 2026-09-20 while verifying NWB-P0-010's owner→invite acceptance path (static review had assumed the endpoint worked). | Team onboarding impossible regardless of F-01/F-08 state |
| **F-21** | H | **Member removal and admin user deletion 500 on an enum violation.** `removeMember` (`DELETE /orgs/:orgId/members/:memberId`) and `deleteUser` (`DELETE /users/:userId`) wrote `status = 'deactivated'`, which is not a `member_status` value (`active | suspended | pending | invited`, PG 22P02) — both routes had failed on every call since they were written. Found 2026-09-20 while making the removal guards of NWB-P0-014 testable. **Fixed in NWB-P0-014**: `status = 'suspended'` + `deleted_at` + `is_active = false` (the pattern `account-deletion.service` already uses; `deleted_at IS NULL` is the membership predicate everywhere). | Team member removal impossible |

**Status as of 2026-09-20:** F-01 **fixed** (NWB-P0-010 — owner role at signup in one atomic block, `organization.owner.created` audit event, 3 new tests incl. forced-rollback atomicity proof). F-02 **fixed** (NWB-P0-011 — route subject corrected to `"org"`, matching the seed's `org.*` permission strings and the compact convention used by every other route; positive `org_admin`→200 and negative `viewer`→403 integration tests added). F-20 **fixed** (schema aligned to the service: 4 invitation-token columns added to `db/organization/organization-members.ts` following the core `tokens` table conventions; `user_id` made nullable to match the service's long-standing `userId ?? null` intent and the spec's pre-acceptance invite lifecycle — the `(organization_id, user_id)` unique index is unaffected because Postgres treats NULLs as distinct). F-20 residual follow-ups for NWB-P0-016: the member list `INNER JOIN users` hides pending invites (needs LEFT JOIN + invited-email display), and re-inviting the same not-yet-registered email creates duplicate pending rows (needs dedup on (org, email) for `status='invited'`). F-07 **fixed** (NWB-P0-014 — DEC-039 role set seeded (`super_admin` + `owner/admin/manager/creator/analyst/viewer`, `org_admin`/`member` retired with memberships re-pointed), guards rewritten in `src/services/orgs/role-policy.ts` against the real codes and applied to *every* role-change and removal path — `assign-role`, `PATCH /members/:id`, `PATCH /users/:id`, `DELETE /members/:id`, `DELETE /users/:id`; 43 pure matrix tests + 15 integration tests. Also fixed en route: the assign-role lookup required `organization_id = orgId`, which no system role satisfies, so the endpoint had 404'd on every request.) F-21 **fixed** (NWB-P0-014, see row). All other findings remain open.

**CASL v7 verification note (for F-02/F-06):** installed `@casl/ability` v7 in an isolated sandbox and executed: rule `can("update","organization",{organizationId:"org-123"})` → `ability.can("update","organization")` ⇒ **`true`** (condition ignored for string subjects), while `ability.can("update","organization",{organizationId:"other"})` throws (object third-arg not a field string) — i.e. the codebase's `requireAbility` pattern can never evaluate conditions. Source: `Rule.matchesConditions` in `@casl/ability` v7 (`if (!s || isSubjectType(s)) { if (!this.inverted) return true; … }`).
