## 5. Defect register (verified in the working tree, 2026-09-20)

Severity: **C**ritical (product unusable / data or security at risk) · **H**igh · **M**edium · **L**ow.
All are pre-existing; none are introduced by this roadmap.

| ID | Sev | Defect | Evidence | Impact |
|---|---|---|---|---|
| **F-01** | C | **Signup creates the owner membership without a role.** `src/services/auth/signup.ts:182` inserts `organization_members (organization_id, user_id, status, is_active)` with no `role_id`. `loadAbility` (`src/services/auth/ability.ts`) derives permissions via `om.role_id → role_permissions`; NULL role ⇒ zero permissions. A brand-new org owner can authenticate but **every `requireAbility`-guarded route returns 403** — they cannot invite members, cannot update the org, cannot manage anything. No test asserts the owner's role after signup (`src/tests/auth/signup.test.ts` has no role/permission assertion). | Onboarding dead-end; the product is unusable after signup |
| **F-02** | H | **Permission subject mismatch: `organization` vs `org`.** `src/app/orgs/org.route.ts:40` calls `requireAbility("update", "organization")`; the seed (`src/seed.ts:63-84` region, `org.read`/`org.update`/`org.delete`) parses in `loadAbility` to subject `"org"`. `ability.can("update","organization")` finds no rule ⇒ **`PATCH /api/orgs/:orgId` 403s for every user, every role.** (Verified against CASL v7 semantics, §5 note.) | Org settings unchangeable via API |
| **F-03** | H | **MFA 2-step login is a dead end — and the single-shot path is a bypass.** `signIn` returns `{requiresMfa:true, sessionId:userId}` with no cookie (`auth.service.ts:158-166`; `signin.route.ts:46-54`), but **no route exists to submit the code**: `confirmMFAChallenge`/`checkMFAForLogin` in `src/services/auth/mfa.ts:175-202` are called from nowhere (grep-verified). Worse, the single-round-trip `mfaCode` path — assumed "working" — never awaited the async `verifyTOTP` (a Promise is truthy, so the `if (!mfaValid)` never fired) and passed its arguments swapped: **any 6-character code completed an MFA login** (found 2026-09-20 while implementing NWB-P0-012; regression test fails against the old code with a 200). **Fixed in NWB-P0-012**: real challenge flow (`mfaSessionId` + `POST /mfa/verify-login`), single-shot path verified via `verifyMFAForLogin` and gated by the AC8 limiter. | MFA users locked out via the documented flow; MFA bypassable via single-shot |
| **F-04** | H | **MFA backup codes: displayed ≠ stored.** `initiateMFASetup` generates and returns codes A (also written to DB, `mfa.ts:30`); `confirmMFASetup` **regenerates a fresh set B and stores B** (`mfa.ts:63`). The user keeps codes A; the DB has B ⇒ every displayed backup code fails. | Backup recovery broken — defeats MFA usability and recovery path |
| **F-04b** | M | **Backup codes stored in plaintext** (jsonb array of UUID slices) vs spec AC4 "stored as bcrypt hashes". | Credential-at-rest exposure |
| **F-05** | H | **User status never enforced at sign-in.** `signIn` selects `status` (`auth.service.ts:73`) but never checks it: `suspended` accounts (settable by admin at `PATCH /api/users/admin/:userId`) and `pending_verification` accounts can authenticate and act. PRD 8.1.1/8.1.2 and Module 1 spec require verified + active for access. | Suspended users retain full access |
| **F-06** | H | **The org-scoping CASL condition is inert.** `loadAbility` attaches `{organizationId: orgId}` to every rule, but `requireAbility` checks `ability.can(action, "string-subject")`. In CASL v7, `Rule.matchesConditions` returns `true` for subject-type (string) subjects whenever the rule is not inverted — the condition is only evaluated for object subjects (verified in `@casl/ability` v7 dist source, `matchesConditions`). Tenant isolation therefore rests **entirely** on JWT-derived `orgId` + `requireOrgMatch` + service-level org predicates (which are all present and correct today). Consequence: the documented 3-layer defense (Security Architecture §4.3) is 2 layers at the API tier; and any future developer who omits `requireOrgMatch` on a new `:orgId` route, believing the ability condition scopes it, will ship a cross-tenant hole. **Closed in NWB-P0-018** (by documentation + tests, as the plan prescribes): the decorative condition is removed from `loadAbility` (behaviour-identical — it was inert), `Security Architecture.md` §4.3 gained an as-built column plus a new §4.3.1 stating the real chain (JWT-derived org → active-principal check → per-(user, org) ability load → `requireOrgMatch` + service org predicates) and marks RLS unimplemented pending D11, the CASL v7 string-subject trap is pinned by a regression test, and `src/tests/route-invariants.test.ts` statically fails any `:orgId` route that omits `requireOrgMatch` — so the 'future developer' failure mode in this row is now caught by CI. | Latent architectural security risk; misleading security docs |
| **F-07** | H | **Role self-protection guards reference role codes that don't exist.** `role-assignment.service.ts` enforces "cannot demote owner" (code `owner`), "owner can't remove own role" (code `owner`), "cannot remove last Admin" (code `admin`). The seeded roles are `super_admin / org_admin / member / viewer` (`src/seed.ts` roleDefs). No role with code `owner` or `admin` exists ⇒ none of the guards can ever fire. Related doc/code conflict: spec calls for a 6-tier hierarchy (Owner, Admin, Manager, Creator, Analyst, Viewer); PRD §8.2.2 for 5 (Owner, Admin, Manager, Analyst, Viewer); seed has 4 different ones. | Lockout protection absent; role model unaligned across all three sources |
| **F-08** | C | **Invitation flow is one-way: no accept endpoint.** `inviteMember`/`bulkInviteMembers` create `organization_members` rows with `status='invited'` + token and email a link to `${CORS_ORIGIN}/invite?token=…` (`invitation.service.ts`), but there is **no service function or route to accept an invitation** (grep-verified: no `accept*invitation` in `src/`). The invitee — whether brand-new or existing user — can never become an active member. Combined with F-01 (no role assignment at join) the whole team onboarding path is broken. | Team onboarding impossible |
| **F-09** | M | **Signup verification email link is broken.** Link base `${config.CORS_ORIGIN}/verify-email?token=…` (`signup.ts:211`); the actual route is `GET /api/auth/verify-email` (`verification.route.ts`). The resend path builds `${origin}/api/auth/verify-email` where `origin` is the **client-sent `Origin` header** (`verification.route.ts:34`) — arbitrary value embedded in a security email. **Closed in NWB-P0-021.** The severity was understated: the same `Origin` base is used by *unauthenticated* `POST /api/auth/forgot-password`, so `Origin: https://evil.example.com` returned 200 and emailed the victim a **valid reset token** on the attacker's domain — reproduced live against pre-fix code, then pinned as a regression test. Fix: a single server-decided `APP_BASE_URL` in `config.ts` (derived `APP_BASE_URL_RESOLVED`, defaults to `CORS_ORIGIN[0]`, trailing slashes stripped, fails closed on a non-URL value). Both routes stopped passing the header, the `origin` parameter was **deleted from the service signatures** so no call site can supply one, the two Server Functions that passed `""` (emitting relative, unclickable links) were fixed too, and the signup link now points at `/api/auth/verify-email` — the route that exists. `src/tests/email-links.test.ts` (12 tests) verifies every `emailService.send` link base and fails if the header ever steers a link again. | Verification emails from signup dead; **valid reset tokens deliverable to an attacker-chosen domain** |
| **F-10** | M | **Inconsistent client-IP extraction.** `signin.route.ts:38` reads `CF-Connecting-IP ?? X-Forwarded-For`; `authMiddleware.clientIp` reads `x-forwarded-for ?? x-real-ip`; no trusted-proxy configuration exists. Behind the documented nginx (Infra §3.5) the rate-limit key and session `ip_address` can disagree per request, and both are spoofable without proxy hardening. | Rate-limit key instability; IP logs unreliable |
| **F-11** | L→**M** | **Route shadowing:** `adminRouter` mounted at `/users` defines `GET/PATCH/DELETE /:userId`; `meRouter` (registered first) owns `/me*`. **Closed in NWB-P0-029 (2026-09-20).** The "harmless today" rating was wrong: `adminRouter`'s list route sat at `/users`, so **`GET /api/users/admin` — the path the API docs advertise — fell through to `GET /:userId` with `userId="admin"` and returned 500** (`22P02 invalid input syntax for type uuid`), reproduced live. Fix: the admin surface gets its own literal prefix (`/users/admin`), so order can no longer decide correctness. **The 500 also exposed a wider defect the shadowing was only one route into:** path params were passed unvalidated into `uuid` columns, so *any* malformed id 500'd. Measured across route families — `users/admin/:userId`, `orgs/:orgId/members/:memberId`, `auth/sessions/:sessionId` and `users/me/data-export/:requestId` all 500'd; only api-keys was safe, because it validated inline. That inline check is now the shared `src/server/api/route-params.ts` helper (`uuidParam`) applied to all four, returning **422** instead. `src/tests/route-params.test.ts` (11 tests) plus 5 in `users/admin.test.ts` pin both halves; both verified red by reverting the mount and the guard separately. | Latent → **was live**: a documented admin endpoint 500'd, and any malformed id reached the driver |
| **F-12** | H | **Rate limiter never engages at all (worse than described).** `checkRateLimit` upsert: `ON CONFLICT (key) DO UPDATE SET count=count+1 … WHERE rate_limits.window_start >= windowStart`, where `windowStart` is freshly computed per call. The stored value predates it by milliseconds, so the `WHERE` never matches and the count sticks at 1 — verified empirically 2026-09-20 (5 attempts, stored count 1, nothing blocked). The "dies after the first window" mechanism in the original description is real but irrelevant: the control is a complete no-op from the first call, so the IP brute-force block (BR-AUTH-018) never fires. (Table itself was only added 2026-09-13 — before that the limiter failed open on every call, per `db/core/rate-limits.ts` header comment.) **Upsert fixed in NWB-P0-012** (adopted 013's specified window-aware statement as the AC8 prerequisite; semantics now fixed clock-anchored windows); **NWB-P0-013** added the reclamation path (`reclaimRateLimits` + `bun run db:reclaim-rate-limits`), dedicated limiter tests (in-window counting, 3 consecutive window boundaries per bucket, reclamation grace — all verified red against the pre-P0-012 statement), and doc updates. F-12 fully fixed. | Brute-force protection never engages |
| **F-13** | M | **CORS is open to all origins.** `app.use("*", cors())` with no options in both app factories (`src/server/index.ts:13,41`); `CORS_ORIGIN` is loaded by `config.ts` but never used. With `SameSite=Strict` cookies the practical XSS-to-session risk is reduced, but the API accepts credentialed cross-origin preflights from any origin. | Over-permissive CORS |
| **F-14** | M | **No pagination on list endpoints** (`GET /api/users/admin`, `/orgs/:orgId/members`, sessions, api-keys return full sets). Fine at beta scale; will degrade. | Scale |

Discovered 2026-09-20 while verifying NWB-P0-010's owner→invite acceptance path (static review had assumed the endpoint worked). | Team onboarding impossible regardless of F-01/F-08 state |

| **F-22** | H | **`tokens.selector` too narrow: every `createToken` call 500s.** `generateSecureToken()` emits 64 hex chars; the column is `varchar(32)` — every insert fails with 22001 (verified empirically 2026-09-20). | **F-23** | M | **`withAtomicWrites` misdetects read-only-so-far transactions and COMMITs the test harness's outer transaction.** The in-tx probe `txid_current_if_assigned() IS NOT NULL` reads NULL until the transaction's first *write*, so any caller that only reads first (every signup test) takes the production path, whose `BEGIN` is a no-op and whose `COMMIT` ends the harness's rollback transaction — silently persisting test data (169 users / 76 orgs of litter found 2026-09-20) and making the suite order-dependent. Found via the fixed F-12 limiter tripping on committed `ip:unknown` litter. **Fixed in NWB-P0-012**: probe replaced with a throwaway SAVEPOINT pair (accepted in-tx, 25P01 outside); full suite re-verified litter-free across repeat runs. | Test isolation silently broken; latent prod stray-COMMIT |
